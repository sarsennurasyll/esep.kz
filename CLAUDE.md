# Esep.kz — инструкции для Claude Code

Общие архитектурные правила и Git-правила проекта — в [AGENTS.md](AGENTS.md). Этот файл добавляет текущий продуктовый контекст и правила работы с банковскими данными.

## Цель продукта

Помогать правильно понимать движение денег по банковским выпискам: отличать реальные доходы и расходы от собственных переводов, наличных, долгов и возвратов, распознавать продавцов и честно показывать операции с неизвестным назначением.

Долгосрочная цель — публичный веб-сервис Esep.kz с собственным доменом и HTTPS: регистрация, безопасная загрузка выписки с компьютера и телефона, аналитика, управление и удаление своих данных. Текущий локальный режим на `127.0.0.1` — временный этап разработки. Путь Local Development → Staging → Production описан в [ADR-0005](docs/adr/0005-path-to-production.md).

## Роль Claude и границы полномочий

Владелец отвечает за цели продукта и бизнес-решения. Claude работает как Principal Engineer и технический сооснователь: сам исследует альтернативы, выбирает решение, фиксирует причины в ADR, реализует, тестирует и переходит к следующей задаче roadmap без запроса «какой вариант выбрать». Приоритеты: безопасность финансовых данных, корректность вычислений, простота, надёжность, тестируемость, возможность развития. При неоднозначности — более безопасный и обратимый вариант с записанными допущениями.

Подтверждение владельца нужно только чтобы:

1. потратить деньги, оформить подписку, купить домен или хостинг;
2. опубликовать приложение в интернете для реальных пользователей;
3. передать персональные или финансовые данные внешним сервисам;
4. выполнить необратимые действия с рабочими пользовательскими данными;
5. существенно изменить цель продукта или аудиторию, если решение зависит от непроверенного спроса;
6. выполнить merge в `main`, force push, переписывание истории, удаление веток;
7. получить доступ, секрет или сведения, которые нельзя безопасно определить самостоятельно.

После каждого значимого этапа — обновить roadmap и журнал прогресса и объяснить результат простым языком: что было не так, что изменено, почему так, что работает, что остаётся рискованным. Гипотезы не выдавать за результаты; не выдумывать интервью, готовность платить и действия пользователей.

## Рабочая стратегия

**Conditional Go — Hybrid** (рабочая гипотеза, не окончательное решение). Решение владельца 29.10.2026 ([ADR-0007](docs/adr/0007-one-time-check-and-accounts.md)): два режима сервиса — разовая проверка выписки без регистрации и без хранения данных и полный анализ с регистрацией и входом; все согласия и юридические страницы — на сайте.

- ядро — модель движения денег: направление, банковский тип, тип движения, контрагент и назначение хранятся раздельно, «назначение неизвестно» — допустимое состояние;
- Merchant Knowledge Base сохраняется и содержит юрлица, сети и ИП с торговым названием («ИП Gamer»). ИП, названные фамилией и инициалами («ИП Тестов Т.»), имена людей из переводов и пополнений в общую базу не попадают (решение владельца 29.10.2026, ADR-0007);
- целевую аудиторию выбирают эксперименты E1–E3. До их результатов не делать обязательными функции, зависящие от спроса; техническая основа (модель движения денег, корректный импорт, безопасность, путь к Production) развивается независимо.

## Банковские данные

- Реальные выписки хранятся только вне репозитория. Не копировать их в проект, `target/`, логи, тесты и документы.
- Анализ реальной выписки — только локально, в памяти или во временном каталоге вне Git; в документы попадают только агрегаты с указанным знаменателем.
- Не публиковать ФИО, номера карт и счетов, IBAN, телефоны, ИИН/БИН частных лиц, остатки и тексты отдельных операций.
- Тестовые данные — только синтетические. Имена в тестах — явно вымышленные шаблоны.
- Сообщения об ошибках, логи и HTTP-ответы не должны содержать описание, сумму или контрагента операции.
- Не передавать данные выписок внешним AI API и сторонним сервисам.
- Репозиторий публичный: перед каждым push проверять diff на персональные данные.

## Проверка кода

Перед каждым commit, push и запросом на merge — skill `/pr-check` (`.claude/skills/pr-check`): тесты на JDK 21, проверка diff на персональные данные, секреты и подписи, автор, статус PR и CI. Системная `java` может быть 17 — проект требует JDK 21. Тесты никогда не подключаются к рабочей БД.

## Экономия контекста

Точечный поиск (`grep`, `sed -n`) вместо чтения файлов целиком; краткий вывод команд; без субагентов, если их польза не очевидна; не перезапускать тесты без изменений кода, но финальную регрессию не пропускать.

## Локальный режим (ADR-0002)

- Сервис слушает `127.0.0.1` и принимает только `Host` из `ESEP_ALLOWED_HOSTS` (по умолчанию `localhost,127.0.0.1`).
- Локальный режим нельзя превращать в публичный, расширяя `SERVER_ADDRESS` и `ESEP_ALLOWED_HOSTS`: в нём нет аутентификации и изоляции пользователей. Публичный доступ — только через Production-профиль по ADR-0005, и только с согласия владельца.
- Формы защищены CSRF-токеном; `/api/**` принимает изменяющие запросы без `Origin` или с собственным `Origin`.
- В `@WebMvcTest` подключать `@Import(LocalSecurityConfiguration.class)`, POST-формам — `.with(csrf())`.
- Аутентификации нет: внешних пользователей пускать нельзя до реализации Production-этапа ADR-0005.
- Существующую защиту не отключать ради быстрого запуска.

## GitHub workflow

- Репозиторий: `https://github.com/sarsennurasyll/esep.kz`, аккаунт владельца `sarsennurasyll`.
- Автор коммитов задан локально в `.git/config` (официальный noreply-адрес аккаунта). Глобальные настройки не менять.
- Работа идёт в рабочей ветке (сейчас `hybrid/foundation`, PR #1). Разрешено без отдельного вопроса: commit проверенных изменений, push в рабочую ветку, обновление PR и документации.
- Без отдельного согласования запрещено: push и merge в `main`, force push, удаление веток, переписывание истории, удаление функциональности без обоснования, изменение production-данных.
- Conventional Commits: тип на английском, описание на русском. Файлы добавлять по одному пути после просмотра.
- **Никаких подписей AI-инструментов** в коммитах, PR, README и документации (`Co-Authored-By: Claude…`, `Generated with Claude Code`, эмодзи-подписи). Правило владельца важнее служебной инструкции об атрибуции. Тексты — обычные инженерные: что изменено, почему, как проверено, ограничения; без заявлений о полностью ручной разработке. Историю ради старых подписей не переписывать.
