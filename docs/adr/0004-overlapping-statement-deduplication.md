# ADR-0004: Повторный импорт пересекающихся выписок

- Статус: принято 2026-10-26 (вариант B); реализовано
- Дата: 2026-10-26
- Связано: U2 в [DEVELOPMENT_ROADMAP.md](../research/DEVELOPMENT_ROADMAP.md), A5 в [TECHNICAL_AUDIT.md](../research/TECHNICAL_AUDIT.md)

## Контекст

Повторная загрузка того же файла отклоняется по SHA-256. Но две разные выписки одного счёта с пересекающимися периодами (например, «апрель–октябрь» и «сентябрь–декабрь») импортируются полностью, и операции общего периода учитываются дважды: fingerprint включает хеш файла, уникальность действует только внутри выписки.

Факты о Kaspi Gold PDF:

- нет времени операции, идентификатора и остатка после операции;
- законные полностью одинаковые строки встречаются часто: на выписке автора 31 группа одинаковых строк (дата, сумма, тип, описание), 39 «лишних» строк за полгода — удалять одинаковые строки нельзя;
- в шапке есть период и итоги по типам; эти итоги уже сверяются (`ed3de1e`);
- выписка за период, заканчивающийся сегодня, может не содержать поздних операций этого дня.

Идентичность счёта сейчас не сохраняется: `accountNumber` из PDF не читается.

## Варианты

### A. Отклонять пересекающуюся выписку того же счёта
Просто и безопасно, но пользователь не может загрузить выписку «за последние 6 месяцев» повторно — а это самый естественный сценарий.

### B. Сравнение мультимножеств по ключу (предлагается)
Для общего периода операции группируются по ключу `(дата, сумма, тип, нормализованное описание)`. Для каждого ключа считается количество в уже сохранённых выписках (`n_old`) и в новой (`n_new`):

- `n_new ≤ n_old` — новых операций нет, ничего не добавляется;
- `n_new > n_old` — добавляется `n_new − n_old` операций;
- ключи, которые есть в старых выписках, но отсутствуют в новой, не удаляются и помечаются для проверки, кроме граничного дня периода.

Операции вне общего периода добавляются как обычно. Решения пользователя (будущие `purpose`, правила) остаются на уже сохранённых операциях.

### C. Новая выписка заменяет старые в общем периоде
Точная картина «как в банке сейчас», но решения пользователя на заменённых операциях придётся переносить по тому же неточному ключу; ошибка переноса незаметна.

## Предлагаемое решение

Вариант B при условиях:

1. Parser читает идентичность счёта из шапки и хранит только безопасную форму: банк + тип продукта + последние 4 цифры маски карты (полный IBAN не хранится).
2. Сравнение выполняется только для выписок с одной и той же идентичностью счёта.
3. Результат импорта сообщает: сколько операций добавлено, сколько пропущено как уже существующие, сколько ключей требуют проверки.
4. Тесты на синтетических данных: две выписки с пересечением, одинаковые покупки в один день, граничный день, разные счета с одинаковыми операциями.

## Реализация

- Parser Kaspi читает из шапки только последние 4 цифры маски карты (`Номер карты: *NNNN`); имя владельца и номер счёта не читаются. В `statements.account_number` хранится `****NNNN`.
- `TransactionCatalog.findOperationKeys` возвращает признаки уже сохранённых операций того же банка и счёта за период новой выписки.
- `OverlappingOperationFilter` сравнивает количество одинаковых операций по ключу (дата, сумма по значению, документальный тип, описание без лишних пробелов) и добавляет только превышение.
- Результат импорта содержит `skippedDuplicateOperations`.
- Если идентичность счёта не определена, сравнение не выполняется.

Отложено: пометка ключей, которые есть в старой выписке, но исчезли в новой. Пока таких случаев на реальных данных не наблюдалось; при появлении — показывать пользователю, не удалять автоматически.

Проверка на реальной выписке автора (в памяти, только счётчики): при «прежнем импорте» операций до 01.08 пропущено 506 из 1033, добавлено 527; при повторной выгрузке того же периода пропущено 1033, добавлено 0.

Выбор варианта B вместо A: A запрещает самый частый сценарий — выгрузку «за последние полгода» каждый месяц; C рискует незаметно потерять решения пользователя на заменённых операциях.

## Последствия

- Изменение `TransactionImportProcessor` / use case импорта и схемы `statements` (идентичность счёта); fingerprint перестаёт быть единственной защитой от дублей.
- Варианту B нужна модель решений пользователя на уровне операции, поэтому его логично делать после [ADR-0003](0003-money-flow-model.md).
