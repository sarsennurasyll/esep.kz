# ADR-0002: Способ обработки и хранения данных выписок

- Статус: предложено, ждёт решения владельца
- Дата: 2026-10-26
- Связано: I4 в [DEVELOPMENT_ROADMAP.md](../research/DEVELOPMENT_ROADMAP.md), S1, S2, S7–S9 в [TECHNICAL_AUDIT.md](../research/TECHNICAL_AUDIT.md)

## Контекст

Esep сейчас — одно Spring Boot-приложение без пользователей: Spring Security исключён, все данные лежат в одной PostgreSQL и видны любому, кто может открыть адрес сервиса. Пока приложением пользуется только владелец на своём компьютере, это терпимо. Ни одного внешнего пользователя в таком виде пускать нельзя.

Ограничения, влияющие на выбор:

- выписка содержит персональные данные владельца и третьих лиц (контрагентов), которые согласия не давали;
- Закон РК № 94-V: хранение персональных данных — на территории РК (ст. 12 п. 2), трансграничная передача ограничена (ст. 16), обязанности оператора по удалению и защите (ст. 25), исключение для обработки исключительно в личных и семейных целях (ст. 3 п. 3 пп. 1) — применимость к сервису требует юридической проверки;
- команда — один разработчик; E1–E2 проводятся без продукта;
- текущий web-слой ходит в собственный REST API по HTTP, что усложняет добавление аутентификации.

## Варианты

### A. Только локальный режим

Приложение запускается у пользователя (как сейчас у владельца), слушает только `127.0.0.1`, данные в локальной БД.

- Плюсы: выписка не покидает устройство; вероятно, подпадает под личное использование; не нужен хостинг в РК.
- Минусы: установка Java, PostgreSQL и Docker неприемлема для массового пользователя; нет синхронизации; CSRF с любого сайта в браузере пользователя остаётся возможным даже при `127.0.0.1`.
- Затраты: низкие на сервер; высокие на упаковку (desktop-сборка или переписывание разбора на JS/WASM для браузера).

### B. Сервер в РК с полным хранением

Многопользовательский сервис: аутентификация, владелец у каждой записи, хранение выписок и операций.

- Плюсы: лучший пользовательский опыт, повторные импорты и правила работают естественно.
- Минусы: полная ответственность оператора персональных данных; шифрование, сроки хранения, удаление, политика, согласие, журнал доступа; хостинг в РК.
- Затраты: самые высокие по поддержке и юридическому оформлению.

### C. Гибрид: разбор без хранения файла, хранение минимального набора

Сервер в РК. PDF разбирается в памяти и не сохраняется. Сохраняются операции пользователя с владельцем, правила и решения. Имена контрагентов-людей хранятся только в пространстве пользователя; в общую базу попадают только организации (уже обеспечено `V11` и `8ac43ca`). Срок хранения и удаление по запросу — обязательны.

- Плюсы: меньше данных под ответственностью; повторное использование правил сохраняется.
- Минусы: всё равно нужна аутентификация, изоляция и юридическое оформление.

## Предлагаемое решение

1. **До результатов E1–E2:** режим A только для владельца. Минимальные меры, не меняющие архитектуру:
   - `server.address` по умолчанию `127.0.0.1`;
   - включить Spring Security с CSRF-защитой для форм и без входа (или с одним локальным паролем) — отдельная небольшая задача;
   - явные лимиты загрузки (`spring.servlet.multipart.max-file-size`, число страниц PDF).
2. **Если E1–E2 подтверждают спрос:** вариант C. Перед первым внешним пользователем — аутентификация, поле владельца во всех таблицах пользователя, фильтр по владельцу во всех read-запросах, тесты доступа к чужим ID, удаление выписки и производных данных, юридическая консультация.
3. Вариант B не выбирать до появления команды и юридического сопровождения.

## Что нужно решить владельцу

- Согласны ли вы с режимом A до результатов экспериментов?
- Разрешаете ли небольшую задачу «Spring Security + CSRF + `127.0.0.1` + лимиты загрузки» сейчас?
- Кто проведёт юридическую консультацию до перехода к C?

## Последствия

- При A не требуется миграция схемы; появляется зависимость от уже подключённого `spring-boot-starter-security`.
- Переход к C потребует миграций (владелец записей), изменения всех read-запросов и web-слоя; HTTP-вызовы web-слоя к собственному API стоит заменить прямыми вызовами сервисов в рамках этой работы.
