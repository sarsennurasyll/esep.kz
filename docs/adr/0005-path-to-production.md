# ADR-0005: Путь от локального режима к публичному сервису

- Статус: принято (техническое решение); покупка домена, хостинга и публикация — только с согласия владельца
- Дата: 2026-10-26
- Связано: [ADR-0002](0002-statement-data-processing-mode.md), [PRODUCT_RESEARCH.md](../research/PRODUCT_RESEARCH.md#право-и-приватность)

## Контекст

Цель владельца — публичный Esep.kz: регистрация, загрузка выписки с компьютера и телефона, аналитика, управление и удаление своих данных. Сейчас приложение работает в локальном режиме ADR-0002: без входа, на `127.0.0.1`, с CSRF, проверкой `Origin` для API и проверкой `Host`. Этого достаточно для разработки одним человеком и недостаточно для любого внешнего пользователя.

Ограничения: финансовые данные разных людей; данные третьих лиц (контрагенты) в выписках; хранение персональных данных — на территории РК (ст. 12 п. 2 Закона № 94-V); команда — один разработчик; спрос не подтверждён (E1–E3).

## Решение

### Окружения

| | Local Development | Staging | Production |
|---|---|---|---|
| Назначение | разработка, тесты, анализ своей выписки | проверка будущей публичной версии | публичный сервис |
| Профиль Spring | по умолчанию (`local`) | `prod` | `prod` |
| Доступ | `127.0.0.1` | закрытый: только владелец (IP-allowlist или basic auth на прокси) | интернет, HTTPS, домен |
| Данные | свои данные владельца или синтетика | **только синтетические** выписки | реальные пользователи |
| Аутентификация | нет (ADR-0002) | как в Production | вход по email и паролю |
| Хостинг | компьютер владельца | ВМ в дата-центре РК | ВМ в дата-центре РК |

Общий код для всех окружений: импорт, модель движения денег, база продавцов, миграции. Различаются только конфигурация безопасности, адрес, секреты и инфраструктура.

**Защитный предохранитель уже сейчас:** локальная конфигурация безопасности не загружается под профилем `prod`, а приложение под `prod` не стартует, пока не реализована Production-безопасность. Так нельзя случайно выставить локальный режим без входа в интернет.

### Архитектура Production (минимальная, с запасом роста)

- **Один сервис** (текущий Spring Boot-монолит), без микросервисов.
- **Одна ВМ в дата-центре РК**: Docker Compose — приложение, PostgreSQL 16, nginx.
- **nginx**: TLS (Let's Encrypt через certbot), HSTS, `client_max_body_size`, `limit_req` для входа, регистрации и загрузки, заголовки безопасности.
- **PostgreSQL**: том на шифрованном диске провайдера; ежедневный `pg_dump` с шифрованием (`age`/`gpg`) в объектное хранилище **в РК**; проверка восстановления раз в месяц. Переход на управляемую PostgreSQL провайдера — когда она появится в РК и нагрузка это оправдает.
- **Секреты**: файл окружения на сервере с правами `600` или хранилище секретов провайдера; в Git и образах секретов нет.
- **Образ** собирается в GitHub Actions и публикуется в GitHub Container Registry; в образе нет данных и секретов. Сервер получает образ по тегу коммита.
- **Мониторинг**: метрики Spring Boot Actuator (без тел запросов и идентификаторов операций), журнал ошибок без данных выписок (уже обеспечено обработчиками ошибок), проверка доступности. Внешние системы мониторинга — только если в них не попадают персональные данные.

Почему не Kubernetes и не PaaS за рубежом: Kubernetes избыточен для одного сервиса и одного разработчика; зарубежный PaaS противоречит требованию хранения в РК.

Кандидаты провайдеров с дата-центрами в РК (условия, цены и наличие объектного хранилища нужно проверить перед выбором; выбор и оплата — решение владельца): QazCloud / VK Cloud Kazakhstan ([новость о запуске](https://hi-tech.mail.ru/news/63112-qazcloud-i-vk-cloud-zapuskayut-lokalizovannuyu-oblachnuyu-platformu-v-kazahstane/)), Pro-Data ([материал](https://digitalbusiness.kz/2025-10-03/lokalnoe-oblako-pro-data-v-kazahstane-nadezhnost-bezopasnost-i-podderzhka-24-7/amp/)), PS Cloud / Hoster.kz (не проверены).

### Безопасность Production

| Механизм | Решение |
|---|---|
| Аутентификация | Spring Security, вход по email и паролю, хеш паролей BCrypt (`DelegatingPasswordEncoder`), сессия на сервере; позже — подтверждение email и второй фактор |
| Сессии | cookie `HttpOnly`, `Secure`, `SameSite=Lax`, смена идентификатора сессии при входе, тайм-аут неактивности |
| CSRF | стандартный CSRF-токен Spring для форм **и** API; проверка `Origin` из локального режима не используется |
| Авторизация и изоляция | у выписки есть владелец; все операции, правила и решения пользователя доступны только через выписки владельца; каждый read-запрос фильтрует по текущему пользователю; тесты доступа к чужим ID (IDOR) |
| Общие данные | база продавцов — только организации (уже обеспечено `V11`, `8ac43ca`); изменять её может только администратор |
| XSS | Thymeleaf экранирует вывод, `th:utext` запрещён; Content-Security-Policy без inline-скриптов |
| SSRF | приложение не загружает URL от пользователя; внутренние HTTP-вызовы web-слоя к собственному API убрать до Staging (вызывать сервисы напрямую) |
| Загрузка файлов | лимиты размера и страниц (уже есть), проверка сигнатуры PDF, таймаут разбора, ограничение частоты загрузок на пользователя, файл не сохраняется |
| Злоупотребления | `limit_req` в nginx; блокировка после серии неудачных входов |
| Хранение и удаление | исходный PDF не хранится; удаление выписки удаляет операции и решения; удаление аккаунта удаляет все данные пользователя; срок хранения неактивных аккаунтов — определить с юристом |
| Право РК | политика обработки персональных данных, согласие при регистрации, хостинг в РК, порядок ответа на запросы субъектов; **юридическая консультация обязательна до Production** |

### Порядок реализации

1. **Сейчас (Local Development):** корректная модель денег и импорта (ADR-0003, ADR-0004), тесты миграций на PostgreSQL (Testcontainers), CI в GitHub Actions, предохранитель профиля `prod`.
2. **До Staging:** пользователи и вход, владелец у выписки, фильтрация всех запросов по пользователю, тесты IDOR; замена HTTP-вызовов web-слоя прямыми вызовами сервисов; стандартный CSRF; Production-конфигурация безопасности; Dockerfile и Compose; удаление выписки и аккаунта.
3. **Staging:** ВМ в РК, только синтетические данные, закрытый доступ, проверка резервного копирования и восстановления, проверка заголовков и TLS.
4. **Production (с согласия владельца):** домен, юридическая проверка, политика и согласие, мониторинг, публикация.

Этапы 2–4 зависят от результатов E1–E2: если спрос не подтвердится, они не начинаются, а вложения в шаг 1 остаются полезными для локальной утилиты.

## Альтернативы

- **Открыть текущее приложение, изменив `SERVER_ADDRESS` и `ESEP_ALLOWED_HOSTS`** — отвергнуто: нет входа и изоляции, любой посетитель увидит все данные.
- **Отдельный фронтенд (SPA) и REST-бэкенд сразу** — отложено: удваивает объём работы; Thymeleaf достаточно для первых пользователей, REST API уже есть для будущего мобильного клиента.
- **Local-first в браузере (разбор PDF на устройстве)** — сильнее по приватности, но требует переписать разбор на JS/WASM; возвращаемся к этому, если E1 покажет, что люди не готовы загружать выписку на сервер.

## Последствия

- Профиль `prod` пока намеренно не запускается.
- Каждая следующая задача безопасности опирается на этот список, а не на расширение локального режима.
