# ADR-0009: Разделение данных по пользователям

- Статус: принято 2026-10-31; реализовано
- Дата: 2026-10-31
- Связано: [ADR-0005](0005-path-to-production.md), [ADR-0007](0007-one-time-check-and-accounts.md), [ADR-0008](0008-accounts-and-login.md)

## Контекст

После ADR-0008 все вошедшие видели одни и те же выписки, операции и правила. Публичный сервис так работать не может: это финансовые данные.

## Варианты

- Параметр владельца в каждом порту и запросе. Явно, но новый запрос без условия молча вернёт чужие данные, а запросов больше тридцати.
- Отдельная схема или база на пользователя. Сильная изоляция, но сложная эксплуатация и миграции; сейчас не окупается.
- Колонка владельца и `@TenantId` Hibernate. Условие добавляется ко всем запросам Hibernate автоматически, а значение при вставке подставляется само.

## Решение

1. **Механизм.** `@TenantId` на `Statement`, `Transaction`, `CounterpartyPurposeRuleEntity`; колонка `owner_id` (миграция `V16`). Владельца сообщает `CurrentOwnerResolver`.
2. **По умолчанию закрыто.** Без вошедшего пользователя владелец несуществующий: запросы ничего не находят, а запись отклоняет внешний ключ.
3. **Гарантии базы.** Внешний ключ на учётную запись; составной ключ `(statement_id, owner_id)` не даёт операции принадлежать не тому, кому принадлежит выписка.
4. **Повторная загрузка.** Хеш файла уникален в пределах владельца: глобальная уникальность раскрывала бы, что такой файл уже загружал кто-то другой.
5. **Чужой id.** Ответ такой же, как на несуществующий: существование чужих данных не раскрывается.
6. **Общая база продавцов.** Менять её может только роль `ADMIN` (адреса из `ESEP_ADMIN_EMAILS`, по умолчанию никто): правка одного пользователя меняла бы результаты всех. Вклад пользователей в базу — эпик 5, по согласию.
7. **Старые данные.** Строки без владельца никому не видны и не удаляются. Их получает учётная запись из `ESEP_LEGACY_DATA_OWNER_EMAIL` при запуске; автоматически отдавать их первому зарегистрированному небезопасно.
8. **Удаление аккаунта.** `POST /account/delete` с подтверждением паролем удаляет одной транзакцией операции, выписки, правила и учётную запись. Общая база продавцов не меняется.

## Последствия

- Обычный SQL обходит фильтр. Он разрешён только там, где это намеренно: удаление аккаунта, передача старых данных, проверка использования продавца всеми пользователями.
- Сопоставление продавца администратором связывает только его собственные операции. У остальных новый продавец распознаётся при следующем импорте.
- Вторая открытая сессия удалённого пользователя живёт до истечения: чтение возвращает пустые списки, запись отклоняет внешний ключ.
- Кнопки правки базы продавцов пока видны всем; без роли `ADMIN` они отвечают 403.
- Разные статусы у разных эндпоинтов на чужой id (404, 400, пустой список) совпадают с ответом на несуществующий id и оставлены как есть.
