# ADR-0003: Модель движения денег

- Статус: предложено, ждёт решения владельца
- Дата: 2026-10-26
- Связано: M2 в [DEVELOPMENT_ROADMAP.md](../research/DEVELOPMENT_ROADMAP.md), A2–A4 в [TECHNICAL_AUDIT.md](../research/TECHNICAL_AUDIT.md), модель в [PRODUCT_STRATEGY.md](../research/PRODUCT_STRATEGY.md#модель-операции-которую-стоит-принять)

## Контекст

Сейчас у операции есть знак суммы, `BankOperationType` (тип из выписки) и `TransactionType` (INCOME / EXPENSE / TRANSFER по знаку). Категория определяется только продавцом. Аналитика считает доходом все поступления, расходом — все списания.

На выписке автора за полгода (агрегаты, см. [TRANSACTION_ANALYSIS.md](../research/TRANSACTION_ANALYSIS.md)): 28,0% суммы поступлений — внесение наличных, 12,6% — поступления с карт других банков, возможно собственных; 19,2% суммы списаний — снятие наличных, 34,7% — переводы людям с неизвестным назначением. Итоги «доход» и «расход» в текущем виде неверны.

Исходные переводы людям привязаны к системному «продавцу» «Переводы людям» с `confidence = 1.0`, хотя назначение неизвестно.

## Решение (предлагается)

У операции четыре независимые оси. Ни одна не выводится из другой автоматически, кроме явно перечисленных правил.

| Ось | Поле | Значения | Кто определяет |
|---|---|---|---|
| Направление | знак `amount` | + / − | банк |
| Документальный тип | `bankOperationType` (есть) | PURCHASE, TRANSFER, TOP_UP, CASH_WITHDRAWAL, OTHER, UNKNOWN | parser банка |
| Тип движения | `flowType` (новое) | PURCHASE, PURCHASE_REFUND, TRANSFER_TO_PERSON, TRANSFER_FROM_PERSON, CASH_DEPOSIT, CASH_WITHDRAWAL, OWN_ACCOUNT_TRANSFER, BANK_FEE, UNKNOWN | правила банка, затем пользователь |
| Назначение | `purpose` (новое) | INCOME_WORK, INCOME_REGULAR, EXPENSE, FAMILY, DEBT, OWN_FUNDS, GIFT, UNKNOWN | пользователь; для покупок — подсказка из категории продавца |

К `flowType` и `purpose` хранятся `source` (BANK_RULE, MERCHANT_KB, PERSONAL_RULE, USER, NONE) и `confidence`. `UNKNOWN` с `source = NONE` — нормальное состояние.

### Детерминированные правила первого шага (Kaspi Gold)

| Условие | flowType | Уверенность |
|---|---|---|
| PURCHASE, сумма < 0 | PURCHASE | высокая |
| PURCHASE, сумма > 0 | PURCHASE_REFUND | высокая |
| CASH_WITHDRAWAL | CASH_WITHDRAWAL | высокая |
| TOP_UP, описание «В Kaspi Банкомате» / «В Kaspi Терминале» | CASH_DEPOSIT | высокая |
| OTHER | BANK_FEE | средняя (тип «Разное» может включать не только комиссии) |
| TRANSFER, сумма < 0 | TRANSFER_TO_PERSON | средняя (может быть собственный счёт) |
| TOP_UP от человека | TRANSFER_FROM_PERSON | средняя |
| «С карты другого банка», имя с указанием другого банка | UNKNOWN, вопрос пользователю «это ваш счёт?» | — |

Правила живут рядом с parser-ом банка (`statementimport/kaspi`) за небольшим интерфейсом вроде `FlowTypeRule`, чтобы новый банк добавлял свои правила, а не правил общие.

### Расчёт итогов

- Доход = операции с `purpose` INCOME_*.
- Расход = PURCHASE − PURCHASE_REFUND + BANK_FEE + переводы с `purpose` EXPENSE.
- Исключаются из обоих: OWN_ACCOUNT_TRANSFER, CASH_DEPOSIT, `purpose` OWN_FUNDS и DEBT.
- Отдельные строки: снятие наличных; семья; поступления и списания с неизвестным назначением.
- Каждый отчёт показывает долю суммы с неизвестным назначением.

### Категория

Категория продавца остаётся подсказкой для покупок. Решение пользователя по конкретной операции хранится на операции и не меняет историю других операций при смене категории продавца.

## Альтернативы

- **Оставить `TransactionType` и дописать исключения в SQL-запросы.** Быстро, но смешивает банковский тип, правила и решения пользователя; не даёт хранить источник решения.
- **Хранить всё в одном поле категории.** Не отличает «не знаю» от «не размечено» и не позволяет считать долю неизвестного честно.

## План внедрения (если решение принято)

1. Миграция: nullable-колонки `flow_type`, `flow_source`, `purpose`, `purpose_source`, `purpose_confidence`; заполнение `flow_type` по правилам для уже сохранённых операций.
2. Правила Kaspi и тесты на синтетических строках.
3. Новые read-запросы аналитики рядом со старыми; старые не удалять до сравнения на выписке автора.
4. Системный получатель «Переводы людям» оставить для совместимости, но не считать такие операции «распознанными» в статистике импорта.

## Что нужно решить владельцу

- Принимаете ли набор значений `flowType` и `purpose` как первую версию?
- Допустимо ли, что после внедрения итоговые доход и расход в интерфейсе заметно изменятся, а часть сумм уйдёт в «неизвестно»?

## Последствия

- Изменение схемы и аналитики — средний объём работы; parser и база продавцов не меняются.
- Пользовательская разметка (E3) получает место для хранения.
- Текущие счётчики «распознано / не распознано» станут честнее и, вероятно, хуже.
