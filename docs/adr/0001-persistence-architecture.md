# ADR-0001: Архитектура persistence для импорта банковских выписок

- Статус: принято
- Дата: 2026-07-27
- Контекст: подготовка к внедрению PostgreSQL persistence после работающего in-memory Import Pipeline

## Контекст

Esep уже умеет извлекать операции из PDF-выписки Kaspi, нормализовать названия продавцов и распознавать их через in-memory Merchant Knowledge Base. Парсинг работает с краткоживущими моделями `ParsedStatement` и `ParsedTransaction`.

Следующий этап — сохранять результаты импорта так, чтобы они стали основой для поиска, аналитики, отчётов, категоризации и пользовательских подтверждений. Persistence не должен менять границы parser-модуля, привязывать бизнес-логику к PostgreSQL или создавать второй параллельный набор доменных моделей.

## Решение

### Цель persistence

Persistence сохраняет подтверждённый результат импорта как предметные данные:

```text
Statement
  └── Transaction
        └── Merchant
              └── Category

Merchant
  └── MerchantAlias
```

`Statement` является записью об импортированной банковской выписке. `Transaction` — долговечная операция, принадлежащая выписке. `Merchant` — элемент базы знаний о продавцах. `Category` относится к продавцу, а не копируется в каждую операцию. `MerchantAlias` хранит варианты названий продавца, встречающиеся в выписках.

`ParsedStatement` и `ParsedTransaction` остаются исключительно транспортными моделями parsing-слоя. Они не сохраняются как доменные сущности, не получают ссылок на `Merchant` или `Category` и не становятся источником аналитики.

### Финальная модель предметной области

Для известного продавца категория получается по цепочке:

```text
Transaction → Merchant → Category
```

Для неизвестного продавца `Transaction.merchant` остаётся пустым. В аналитике такая операция относится к системной категории `UNCATEGORIZED`. После появления нового подтверждённого `Merchant` операция может быть связана с ним отдельным процессом обогащения; это не входит в первый persistence-этап.

Категория не добавляется в `Transaction`. Это исключает дублирование значения категории, позволяет исправлять классификацию на уровне базы знаний о продавце и сохраняет единственный источник истины.

### Контракт идентификации Merchant

JPA-сущность `Merchant` использует технический primary key `Long id`. Текущий in-memory `MerchantMatch` использует строковый идентификатор, который является деталью тестового каталога и не может напрямую использоваться как JPA ID.

Финальный прикладной контракт — непрозрачный value object `MerchantReference`. `MerchantResolver` возвращает эту ссылку только для распознанного продавца; потребители не интерпретируют её значение и не строят поиск по `displayName`. `MerchantCatalog` принимает `MerchantReference` и возвращает продавца в своей модели.

In-memory адаптер сопоставляет `MerchantReference` со строковым ID записи. PostgreSQL/JPA адаптер сопоставляет ту же непрозрачную ссылку с `Merchant.id`, не раскрывая тип primary key за пределами adapter boundary. Строковый ID в `MerchantMatch` заменён на этот контракт подготовительной задачей перед persistence-портами.

### Стратегия хранения Category

Категория хранится в существующей сущности `Category` и связывается с `Merchant` через `Merchant.category`. Для долгосрочной интеграции каталогов каждая категория получит неизменяемый уникальный технический ключ `code`, например:

```text
code: GROCERY
name: Продукты
```

Имена категорий могут переименовываться и локализоваться, поэтому `name` не используется как постоянный машинный идентификатор. `UNCATEGORIZED` будет системной активной категорией, создаваемой миграцией данных.

До появления базы данных встроенный каталог должен ссылаться на ключ категории, а не дублировать полноценную модель `Category`.

### Стратегия хранения accountNumber

Номер счёта относится к выписке и будет храниться в `Statement`, а не в каждой операции. Значение содержит персональные финансовые данные, поэтому в первом persistence-релизе оно хранится в маскированном виде, достаточном для интерфейса и диагностики, например `****1234`.

Полный номер счёта не сохраняется, пока отдельно не будут определены требования к шифрованию, управлению ключами, срокам хранения и доступу к персональным данным.

### Стратегия определения TransactionType

`TransactionType` определяется в bank-specific parsing/interpretation слое до создания JPA `Transaction`. Общая классификация использует только существующие значения `INCOME`, `EXPENSE`, `TRANSFER` и `UNKNOWN`.

Первичная реализация использует детерминированные признаки конкретной выписки: знак суммы и тип операции, извлечённый Kaspi parser. Если формат не позволяет сделать надёжный вывод, сохраняется `UNKNOWN`; запрещено угадывать тип операции с помощью AI.

### Идемпотентность импорта

Повторная загрузка того же файла не должна создавать вторую выписку и дублировать операции. Основной механизм — криптографический отпечаток исходного файла `sourceFileHash`, вычисляемый из байтов до parsing.

Перед сохранением `Statement` persistence layer проверяет наличие выписки с таким отпечатком. При совпадении новый импорт не создаёт данные и возвращает контролируемый результат повторного импорта.

Дополнительный fingerprint операции рассматривается как вторая линия защиты для будущих файлов с одинаковыми операциями, но разными именами или составом. Он не заменяет file hash в первом persistence-релизе.

### Дата операции

Для текущего этапа датой операции выбирается `LocalDate`. Реальные Kaspi PDF-выписки дают календарную дату без времени и часового пояса. Использование `LocalDateTime` привело бы к искусственному времени `00:00`, создающему ложную точность и проблемы при будущей аналитике.

Когда банк начнёт предоставлять надёжное время операции, оно будет добавлено отдельным необязательным полем. Уже сохранённая дата останется корректной.

До реализации извлечения периода из заголовка PDF период выписки вычисляется в application layer по операциям: `periodFrom` — минимальная `transactionDate`, `periodTo` — максимальная `transactionDate`. Выписка без операций считается некорректной и не импортируется.

### Границы Import Pipeline и Persistence Layer

Import Pipeline сохраняет текущую ответственность:

```text
PDF/InputStream → StatementParser → ParsedStatement → StatementImporter → MerchantRecognitionService → ImportResult
```

Он извлекает и валидирует данные, нормализует название, распознаёт продавца и формирует статистику. Он не зависит от JPA, PostgreSQL, Spring Data или SQL.

Persistence Layer начинается после успешного parsing и recognition. Будущий application use case создаёт `Statement`, преобразует `ParsedTransaction` в `Transaction`, устанавливает найденный `Merchant` и сохраняет агрегат в одной транзакции. Он использует порты, но не обращается к конкретным JPA-репозиториям напрямую.

Повторное выполнение recognition в разных слоях не допускается. При реализации application use case текущая оркестрация должна быть вынесена или переиспользована так, чтобы продавец распознавался ровно один раз на операцию.

### Необходимые Ports

Для persistence понадобятся небольшие прикладные интерфейсы:

- `StatementCatalog` — поиск выписки по отпечатку исходного файла и сохранение выписки;
- `TransactionCatalog` — пакетное сохранение операций;
- `MerchantCatalog` — получение продавца по `MerchantReference`;
- `MerchantAliasCatalog` — доступ к алиасам при распознавании и их последующем подтверждении;
- `CategoryCatalog` — получение категории по стабильному `code`;
- `ImportTransactionManager` — граница атомарной записи выписки и её операций, если она не будет скрыта в application service.

In-memory реализации остаются для unit-тестов. PostgreSQL/JPA реализации будут адаптерами этих контрактов. Названия и окончательная декомпозиция портов уточняются вместе с контрактом идентификации Merchant, без смешивания портов с Spring Data interfaces.

## Изменения JPA-модели следующего этапа

Следующая задача должна внести согласованный набор изменений вместе с миграциями:

1. Прикладной контракт: заменить строковый ID в `MerchantMatch` на `MerchantReference` и адаптировать текущие in-memory каталоги без изменения resolver-алгоритма.
2. `Category`: добавить неизменяемый уникальный `code`; создать системную категорию `UNCATEGORIZED`.
3. `Statement`: добавить маскированный `accountNumber` и уникальный `sourceFileHash`.
4. `Transaction`: заменить `transactionDate` с `LocalDateTime` на `LocalDate` либо согласовать эквивалентную модель даты без фиктивного времени.
5. `Transaction`: определить технический уникальный fingerprint операции как дополнительную защиту от дубликатов.
6. `MerchantAlias`: добавить `verified`, если пользовательские подтверждения алиасов входят в ближайший этап.
7. Индексы и ограничения: добавить уникальность для `sourceFileHash`, а также согласованные ограничения для fingerprint операции.

Изменения сущностей и схемы выполняются только через versioned migrations. Flyway или Liquibase выбирается и подключается до первой persistence-миграции.

## Отложенные решения

Следующие решения сознательно не входят в первый persistence-этап:

- шифрование полного номера счёта и политика хранения персональных данных;
- хранение времени операции и timezone;
- история изменения категории продавца и category snapshot на уровне операции;
- пользовательские category overrides;
- автоматическое создание нового Merchant для неизвестной операции;
- подтверждение алиасов пользователями, рейтинги доверия и аудит решений;
- optimistic locking для конкурентного обновления счётчиков Merchant;
- fuzzy matching, rule engine и AI;
- стратегическое решение о batch processing для очень больших выписок.

## Последствия

Решение сохраняет единый источник истины для категории на уровне `Merchant`, не меняет существующие parser-модели и изолирует PostgreSQL за портами. Цена решения — необходимость до persistence уточнить merchant identifier и добавить несколько полей в JPA-модель. Эта цена ниже, чем будущая миграция от временных import-моделей или дублированных категорий в операциях.
