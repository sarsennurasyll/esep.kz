# Продуктовая стратегия Esep.kz

Опирается на [PRODUCT_RESEARCH.md](PRODUCT_RESEARCH.md), [TRANSACTION_ANALYSIS.md](TRANSACTION_ANALYSIS.md) и [TECHNICAL_AUDIT.md](TECHNICAL_AUDIT.md). Оценки трудозатрат — сценарии при явных допущениях, не обязательства.

## Главный вывод

Текущий тезис продукта — «главная ценность в Merchant Knowledge Base Казахстана» — данными не подтверждается:

- по сумме списаний автора распознаванию продавца в принципе поддаются только покупки (46%); переводы людям (34,7%) и наличные (19,2%) база продавцов не объясняет;
- покупки Kaspi уже категоризирует сам, бесплатно и с лучшими исходными данными (MCC, эквайринг);
- seed-база распознаёт треть покупок даже на выписке, по которой она, вероятно, составлена, а нормализация не дала ни одного объединения;
- основная неопределённость — назначение переводов и поступлений, а её невозможно устранить ни базой продавцов, ни AI: этой информации нет в документе.

Реальная проблема, которую выписка позволяет решать достоверно, — **правильно разделить потоки денег** (свои перемещения, наличные, покупки, переводы людям) и **помочь пользователю быстро разметить то, что знает только он**, особенно входящие деньги.

## Модель операции, которую стоит принять

Каждая операция описывается независимыми осями; ни одна не выводится из другой автоматически.

| Ось | Значения | Источник истины | Уверенность |
|---|---|---|---|
| Направление | входящая / исходящая | знак суммы | факт |
| Банковский тип | покупка, перевод, пополнение, снятие, разное, неизвестный тип банка | текст выписки | факт |
| Движение денег | покупка, возврат покупки, перевод человеку, поступление от человека, внесение наличных, снятие наличных, свой перевод, комиссия банка, проценты, кредит/займ | правила + пользователь | высокая для наличных, комиссий, возвратов; низкая для своих переводов без подтверждения |
| Контрагент | продавец-юрлицо (общая база), ИП (личное пространство), физлицо (личное пространство), собственный счёт, банк | база, правила, пользователь | отдельный `confidence` идентификации |
| Назначение / категория | категория расходов, доход, долг выдан/возвращён, подарок, семья, **«назначение неизвестно»** | пользователь; для продавца — подсказка из базы | отдельный `confidence`; явный отказ — нормальное состояние |

Расчёт итогов из этой модели:

- **доход** — только поступления, размеченные как доход; неразмеченные поступления от людей показываются отдельной строкой «поступления с неизвестным назначением»;
- **расход** — покупки минус возвраты + переводы, размеченные как расход; снятие наличных — отдельная строка «наличные, назначение неизвестно»;
- **исключаются из обоих** — свои переводы, внесение собственных наличных, перемещения между счетами, выдача и возврат долга;
- в каждом отчёте — доля суммы с неизвестным назначением, чтобы пользователь видел, насколько отчёт достоверен.

## Поведение при недостатке уверенности

- Вопрос пользователю формулируется про контрагента, а не про строку: «Поступления от контрагента N: 12 операций за полгода. Что это обычно?» с вариантами «мой другой счёт», «доход за работу», «семья», «возврат долга», «разное — спрашивать по каждой», «не знаю».
- Ответ создаёт личное правило с областью действия (контрагент; опционально направление и диапазон сумм) и видимым списком затронутых операций. Исключение для одной операции не ломает правило.
- Каждое решение хранит источник (правило, база, пользователь), время и предыдущее значение; отмена — одно действие.
- Отказ («не знаю») — валидное состояние, а не ошибка. Система не подменяет его угадыванием.
- Вопросы упорядочены по сумме: на данных автора 12 ответов о источниках поступлений покрывают 90% входящей суммы, 26 ответов о получателях — 90% суммы переводов.

## Стратегии

### A. Minimal MVP — «разбор поступлений и личного/делового на Kaspi Gold»

| | |
|---|---|
| Целевой пользователь | физлица и ИП, которые получают оплату переводами на личную карту Kaspi Gold |
| Проблема | показать, какие поступления — доход, а какие — свои деньги, семья, долги; подготовить понятный отчёт за период |
| Функции | надёжный импорт одной выписки Kaspi Gold со сверкой итогов шапки; модель движения денег; разметка контрагентов по сумме; личные правила с отменой; отчёт «доход / свои деньги / неизвестно» с долей неопределённости; удаление выписки |
| Исключено сознательно | AI, общая база с людьми, другие банки, аналитика покупок (её даёт Kaspi), советы и прогнозы, налоговые расчёты |
| Зависимости | аутентификация, хостинг в РК или локальный режим, юридическая проверка формулировок |
| Сложность | Г: 4–6 недель одного разработчика на неполный день при сохранении текущего стека и без мобильного приложения |
| Технические риски | изменения формата PDF Kaspi; производительность и безопасность загрузки |
| Продуктовые риски | сегмент может не захотеть загружать выписку; задача редкая (раз в полгода); может оказаться, что достаточно таблицы |
| Затраты, сценарии | Г: инфраструктура — один небольшой сервер и PostgreSQL в РК; без AI переменные затраты близки к нулю; основная стоимость — время разработки и привлечение первых пользователей |
| Успех | ≥5 из 15 опрошенных из сегмента пройдут полный сценарий на своей выписке и скажут, что отчёт им пригодился; разметка ≤20 минут на полгода |
| Отказ | меньше 3 из 15 испытывают проблему; пользователи не готовы загружать выписку ни в локальном, ни в серверном режиме |

### B. Balanced Product — «честная картина денег по нескольким счетам»

| | |
|---|---|
| Целевой пользователь | A + семьи и люди с несколькими счетами Kaspi и другими банками |
| Проблема | повторяемая месячная картина без двойного учёта |
| Функции | A + повторный импорт с дедупликацией между выписками, несколько счетов, сопоставление своих переводов между ними, база продавцов только для юрлиц, UX подтверждений, шифрование и сроки хранения, проверяемая аналитика |
| Исключено | AI для переводов, B2B API, прогнозы |
| Зависимости | образцы выписок других счетов и банков; модель контрагента и личных правил |
| Сложность | Г: ещё 2–3 месяца после A |
| Риски | каждый новый формат банка — отдельная поддержка; банки могут добавить свою аналитику переводов |
| Успех | ≥40% пользователей A возвращаются со следующей выпиской; повторный импорт требует ≤5 новых ответов |
| Отказ | возврат <20% после второго периода |

### C. Long-term Platform — «Merchant Intelligence для Казахстана»

| | |
|---|---|
| Целевой пользователь | банки, финтех, бухгалтерские сервисы (B2B/API) |
| Проблема | обогащение транзакций названием и категорией продавца |
| Функции | многобанковый разбор, масштабная база юрлиц, API, SLA |
| Зависимости | доступ к большим объёмам транзакций, договоры с источниками данных, юридическое оформление обработки чужих данных |
| Сложность | Г: команда и год+ работы |
| Риски | у банков данные лучше (MCC, эквайринг); нет источника качественного пополнения; конкуренты-провайдеры обогащения |
| Успех | подписанный пилот с одним B2B-клиентом на его данных |
| Отказ | ни один потенциальный клиент не готов к пилоту |

Сейчас для C нет ни данных, ни преимущества. Возвращаться к нему имеет смысл, только если B соберёт заметную базу пользователей и подтверждённых юрлиц.

## Выбор аудитории

**Начальная аудитория: физлица и ИП на упрощённом режиме, которые принимают оплату за товары и услуги переводами на личную карту Kaspi Gold.**

Почему: у этой задачи есть цена ошибки (контроль входящих переводов физлиц с 2026 года по вторичным источникам), выписка содержит нужные данные о поступлениях, а Kaspi, по найденным данным, не решает разметку поступлений на личную карту. Слабые стороны: задача редкая, нужно доверие к загрузке, а формулировки близки к налоговым консультациям — их нужно проверить юридически.

Если интервью покажут, что этим людям достаточно таблицы или бухгалтера, лучшим продуктом может оказаться не сервис, а локальная утилита (desktop/CLI или браузерная страница без сервера), превращающая PDF в размеченную таблицу. Это дешевле и честнее по приватности.

## Ответы на ключевые вопросы

1. **Продолжать ли Esep.kz в нынешнем виде?** Нет. Нынешний вид — PFM с базой продавцов и наивной аналитикой — дублирует бесплатную аналитику Kaspi и не работает на реальной выписке. Кодовую базу стоит сохранить, позиционирование — сменить.
2. **Какая боль сильнее всего?** Г: непонимание входящих денег и смешение своих, семейных и деловых потоков на одной карте. Подтверждать интервью.
3. **Почему будут возвращаться и доверять?** Г: возвращаться — к сроку отчётности или при запросе налоговой, с сохранёнными правилами; доверять — за счёт сверки с итогами шапки, видимой доли неизвестного, объяснения каждого решения, локального или краткосрочного хранения.
4. **Что реально даёт шестимесячная история?** Повторяемость контрагентов: 22 источника поступлений покрывают 90,6% входящих операций; 80,5% поступлений второй половины периода приходят от уже знакомых источников. Для покупок и переводов повторяемость ниже (47,5% и 37,7%).
5. **Какие назначения нельзя восстановить автоматически?** Назначение переводов людям и поступлений от людей; что сделано с наличными; состав покупки; принадлежит ли карта другого банка самому пользователю; займ это, подарок или оплата.
6. **Как быть полезным при высокой доле неизвестного?** Показывать неизвестное как отдельную величину, а не прятать в «Без категории»; правильно исключать собственные перемещения; спрашивать о самых крупных контрагентах первыми.
7. **Долгосрочная защита?** Сильной защиты не видно. Слабые источники: личные правила и история пользователя, доверие к приватности, качество разбора форматов банков РК.
8. **Что сохранить, а что менять?** Сохранить контракт парсера и реестр, неизменяемые модели разбора, порты, `BigDecimal`, Flyway, SHA-256 файла. Менять позже: модель операции (оси выше), отделение контрагентов-людей от общей базы, категорию на уровне операции, дедупликацию между файлами, web-слой без HTTP-вызова самого себя, мёртвый пакет `parser`.
9. **Что исключить из MVP?** AI, общую базу людей, другие банки, аналитику покупок, рекомендации, прогнозы, мобильное приложение, B2B API.
10. **Какие исследования нужны до серьёзной разработки?** Интервью с сегментом, ручной (concierge) отчёт по их выпискам, измерение времени разметки, образцы выписок на трёх языках, юридическая консультация по ст. 3, 12, 16 Закона № 94-V и по формулировкам о доходе. Детали — в [DEVELOPMENT_ROADMAP.md](DEVELOPMENT_ROADMAP.md#решающие-эксперименты).
11. **Когда делать Pivot дальше или закрывать?** Если меньше 3 из 15 человек сегмента подтверждают проблему; если никто не готов загрузить выписку даже в локальном режиме; если в Kaspi появляется разметка поступлений по контрагентам; если юрист видит в сервисе недопустимую налоговую консультацию.

## Решение

**Pivot.**

Продолжать проект, но не как «аналитику расходов на базе Merchant Knowledge Base», а как инструмент честного разбора потоков денег на личной карте с фокусом на поступления, начиная с одной аудитории (стратегия A). Разработку новых функций не начинать до результатов экспериментов E1–E3.

Решение пересматривается:

- в сторону **Go** по стратегии A — если E1 и E2 проходят критерии успеха;
- в сторону **No-Go** — если E1 не проходит критерий или E2 показывает, что отчёт не нужен даже бесплатно;
- в сторону **B** — после 60 дней, если повторное использование правил подтверждается на выписках других людей.
